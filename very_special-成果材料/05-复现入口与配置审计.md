## 一键入口

评审者可在 VS Code 中使用 `Terminal -> Run Task`：

| 可点击任务 | 实际命令 | 覆盖内容 |
| --- | --- | --- |
| `Competition: Run Task 1` | `scripts/competition/task123.sh suite task1` | RR/FP-RR 3+3 |
| `Competition: Run Task 2` | `scripts/competition/task123.sh suite task2` | 无模型正常链路 + 五类故障 |
| `Competition: Run Task 3` | `scripts/competition/task123.sh suite task3` | ncnn/YOLO smoke + 模型拒绝；不包含联合正常闭环 |
| `Competition: Run Full Validation` | `scripts/competition/task123.sh suite full` | 全部十个行为场景 |

单独运行 Task2+Task3 联合正常闭环：

```bash
scripts/competition/task123.sh run task23-integrated
```

命令行推荐顺序：

```bash
scripts/competition/task123.sh doctor
scripts/competition/task123.sh build full
scripts/competition/task123.sh suite full
```

`doctor` 只检查环境；`build full` 保留已下载源/工具链，但从当前 checkout 重新生成产物；`suite full` 任一场景失败即非零退出。`ci-contracts` 是独立 gate，不算十个行为场景之一。

## 宿主机可配置字段

仓库默认路径由脚本位置推导 `repo_root`，不依赖调用者当前目录，也不把开发者用户名写进可执行配置。

| 类别 | 环境字段 |
| --- | --- |
| AArch64 musl 工具链 | `CROSS_ROOT`、`CROSS_CC`、`CROSS_CXX`、`CROSS_AR`、`CROSS_RANLIB`、`CROSS_COMPILE` |
| 外部源/工具 | `NCNN_SOURCE`、`ZEPHYR_BASE`、`PNNX`、`YOLO_ONNX` |
| ncnn smoke 输入 | `TASK3_NCNN_INPUT` |
| 证据/短运行 | `TASK123_EVIDENCE_DIR`、`TASK123_RUNTIME_PARENT` |
| QEMU 资源互斥 | `TASK123_QEMU_LOCK_FILE`、`TASK123_QEMU_LOCK_TIMEOUT_SEC` |
| QEMU/Guest 输入 | `STARRY_TASK23_ROOTFS`、`STARRY_TASK23_HOST_CONFIG`、`STARRY_TASK23_QEMU_CONFIG`、`STARRY_TASK23_STARRY_VM_CONFIG`、`STARRY_TASK23_RTOS_VM_CONFIG` |
| RTOS 选择 | `STARRY_TASK23_RTOS_NAME`、`STARRY_TASK23_RTOS_IMAGE`、`STARRY_TASK23_RTOS_SOURCE_DIR` |
| 运行策略 | `STARRY_TASK1_PERIODIC_REPEATS`、`STARRY_TASK23_SERIAL_SOCKET_TIMEOUT`、`STARRY_TASK23_COLLECT_RT_STAT` |

`CROSS_ROOT` 在统一入口展开为工具路径并贯通到 ncnn smoke。可移植示例：

```bash
export CROSS_ROOT="$PWD/tmp/competition-task123/downloads/aarch64-linux-musl-cross"
export NCNN_SOURCE="$PWD/tmp/competition-task123/downloads/ncnn"
export ZEPHYR_BASE="$PWD/tmp/competition-task123/downloads/zephyr-pinned"
export PNNX="$PWD/tmp/competition-task123/downloads/pnnx/pnnx"
export YOLO_ONNX="$PWD/tmp/competition-task123/downloads/yolo11n.onnx"
```

## QEMU 资源互斥

该主机约有 15 GiB 物理内存，单次验收 QEMU 使用 `-m 8g`。两个 QEMU 并发时 swap 曾用满 `4/4 GiB`，导致串口进度 watchdog 假超时。

评委入口现在通过 `TASK123_QEMU_LOCK_FILE` 使用同一把 `flock`，并用 `TASK123_QEMU_LOCK_TIMEOUT_SEC` 限制等待时间。真实重跑中，另一 Task1 诊断被正确串行化，没有通过放大 watchdog 来隐藏资源问题。

## 运行时路径和并发隔离

QEMU/AxVisor 运行 TOML 必须引用实际 rootfs、Guest 和 socket，所以渲染后配置会出现本机绝对路径。它们由本次输入解析生成，不是提交内硬编码；证据同时保存 source TOML 和 runtime TOML。

每次 QEMU 运行通过 `mktemp` 创建独占目录，serial、QMP socket、可写 rootfs 副本和 pcap 不共享。清理只针对本次 PID，不使用全局 `pkill`/`killall`。

## 有意冻结的契约

`10.0.42.15/24`、`10.0.42.2/24`、UDP `4242` 和 Guest 模型目录 `/usr/share/task3-yolo` 是线协议或镜像 ABI，不是开发机硬编码。修改它们必须同时更新两 Guest、fixture、pcap verifier 和镜像构建，不宜由单端环境变量静默覆盖。

## 物理板边界

实板输入由 `STARRY_KERNEL`、`STARRY_INITRD`、`ATK_HOST_DTB`、`ZEPHYR_BASE` 覆盖，板卡选择由 `ATK_PORT`、`ATK_BAUD`、`ATK_FASTBOOT_SN` 指定。只允许 `scripts/board/atk-dlrk3588-ram-boot.sh` 的 RAM-only `fastboot stage`，不使用 flash/erase。

当前实板仅可声称 Task1 periodic RR/FP-RR 各3轮 PASS。Task2/3 完整矩阵未完成，旧 RR 运行有 RKNN sequence error，ext4 `EUCLEAN` 仍是 UNRESOLVED。
