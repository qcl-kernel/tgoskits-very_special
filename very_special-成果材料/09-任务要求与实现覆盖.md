# OpenCamp 任务要求与实现覆盖

> 项目：智能化工控中基于虚拟化的混合系统部署及联动实现
>
> 官方页面：<https://opencamp.cn/qcl/camp/OpenRace2026/stage/1>
>
> 页面核对日期：2026-08-25

本文把官网对系统能力的要求与已完成的
设计、代码、运行结果和复现入口建立对应关系。这样可以直接看到系统
做了什么、为什么这样做，以及在哪里查看真实实现。

## 1. 完整系统主线

```text
                              RK3588
+--------------------------------------------------------------------+
| pCPU2：类 Linux StarryOS vCPU0                                  |
|   图像 -> 预处理 -> RKNN -> NPU -> 检测 -> 安全决策             |
|                                      |                             |
|                                      v                             |
| pCPU1：共享实时通信域                                           |
|   StarryOS vCPU1 ---- T2N1 CONTROL ----> Zephyr RTOS vCPU0         |
|   VirtIO-net       <---- ACK/STATUS ---- 控制执行/10 ms 周期      |
|       priority 89       AxVisor FP-RR       priority 90            |
|                                                                    |
| RK3588 NPU：只归 StarryOS，不是 pCPU，不分配给 Zephyr          |
+--------------------------------------------------------------------+
```

Task 1、Task 2 和 Task 3 不是三个彼此独立的 Demo，而是一条工业控制
链路的三个层次：

- Task 1 提供可预期的调度、定时器和中断底座；
- Task 2 提供可靠、有隔离边界的双向 IP 控制通道；
- Task 3 把真实图像感知转换为 RTOS 可执行、可拒绝、可锁存的安全动作。

## 2. Task 1：实时底座的完整工作

| 要求范围 | 我们完成的工作 | 主要实现位置 | 可观察结果 |
| --- | --- | --- | --- |
| 调度与抢占 | 实现 bounded FP-RR：高优先级唤醒抢占、同优先级 RR、低优先级有界服务 | `components/axsched/src/priority_rr.rs`、`components/axsched/src/tests.rs` | 正式实板 P99 `0.621 -> 0.278 ms`，降低 55.3% |
| 唤醒与 IRQ-tail | 高优先级 RTOS 在唤醒点和中断退出边界及时获得 CPU | `virtualization/axvm/src/runtime/vcpus.rs`、`virtualization/axvm/src/irq/` | P99.9 `7.816 -> 0.748 ms`；FP-RR 各次运行无 deadline miss |
| AArch64 虚拟定时器 | 修复 CNTV 激活所有权泄漏，将 acknowledge、retire、deactivate 状态转换显式化 | `virtualization/axvm/src/arch/aarch64/vtimer/` | 共享 CPU 上的 10 ms 周期中断不再因激活泄漏停止 |
| 虚拟中断可靠性 | 引入有界 pending queue 和 queue 之外的 retry slot，处理 GIC LR 暂时不可用 | `virtualization/axvm/src/runtime/dispatcher.rs`、`virtualization/axvm/src/architecture/ops.rs` | 中断边沿不因队列竞争静默丢失，队列大小可观测 |
| 锁与关键路径 | 把 wake/notify/IPI/IRQ complete 移出宽锁范围，缩小调度敏感临界区 | `virtualization/axvm/src/runtime/`、`virtualization/axvm/src/arch/aarch64/gic/` | 避免通知回调与 VM 运行时锁交叉阻塞 |
| CPU 亲和性 | 将 StarryOS AI vCPU、通信 vCPU 和 Zephyr 明确绑定到对应 pCPU，优先级由配置决定 | `scripts/board/task123-zephyr/*.toml.in`、`virtualization/axvm/src/config.rs` | 运行时拓扑可与配置和证据 manifest 直接对账 |
| 多核 StarryOS Guest | 启动 2-vCPU StarryOS，划分 1 GiB 内存、NPU/eMMC/VirtIO 设备和中断所有权 | `scripts/board/task123-zephyr/starry.toml.in` | vCPU0 承担 AI，vCPU1 承担通信，两者职责可独立观测 |
| 测量与长尾 | 周期任务记录 mean/P50/P95/P99/P99.9/max、`>1 ms`、deadline miss 和负载活性 | `scripts/test/rt-partition/`、`scripts/test/net-dual-guest/analyze_starry_task1_periodic_ab.py` | 每种调度方式运行 3 次，每次 6000×10 ms |
| 原生 RTOS 基线 | Zephyr 在等价 QEMU AArch64 平台上直接运行，不经过 AxVisor | `scripts/test/rt-partition/run-native-zephyr.sh` | 原生、AxVisor RR、AxVisor FP-RR 各 6000 样本；无竞争时 RR/FP-RR 接近 |

正式架构主动把 AI CPU 工作隔离到 pCPU2，只让通信 vCPU 与 Zephyr
在 pCPU1 共享。高竞争实验显示了调度机制在重压下的作用，但不用它
定义产品架构。详细理由和数据见 [01-Task1-实时调度设计与结果.md](01-Task1-实时调度设计与结果.md)。

## 3. Task 2：网络、协议、可靠性与隔离

| 要求范围 | 我们完成的工作 | 主要实现位置 | 可观察结果 |
| --- | --- | --- | --- |
| 双向 IP 链路 | StarryOS 和 Zephyr 分别拥有 VirtIO-net endpoint，经 AxVisor L2 switch 交换 UDP/IPv4 | `apps/starry/starryos-task2/`、`scripts/test/net-dual-guest/zephyr-task2/` | CONTROL 向 RTOS 流动，ACK/STATUS 反向回传 |
| 明确的数据面 | 主通道不使用共享内存、HyperCall、裸 MMIO 或 vsock | `docs/design/task2-dual-guest-network-final.md` | UART 只用于启动与证据采集，不冒充业务链路 |
| T2N1 线格式 | 实现 28 B 定长头、网络字节序、CRC32、版本、类型、session、sequence、ack、length 和 error | `components/task2-net-protocol/src/frame.rs` | CONTROL、STATUS、ERROR、ACK、HEARTBEAT 均可解析和对账 |
| 类型化 payload | Control/Status/Heartbeat 使用定长类型并验证 action、state、value 和 request ID | `components/task2-net-protocol/src/payload.rs` | 越界参数在执行前被拒绝 |
| UDP 可靠性 | stop-and-wait、ACK、500 ms timeout、最多 5 次重传、重复抑制、乱序拒绝 | `components/task2-net-protocol/src/session.rs` | 丢 ACK、重试耗尽和乱序场景均有明确状态转换 |
| 存活与恢复 | 200 ms HEARTBEAT、5 s peer timeout、Safe 状态、恢复后 sequence 重新同步 | 协议 session 与两端 endpoint | blackout 与合法链路恢复均可复现 |
| 网络隔离 | 两端使用独立 virtqueue、DMA 区间、stage-2 映射和 vIRQ，NPU 不暴露给 RTOS | VM TOML、FDT 和 isolation verifier | MAC/IP/UDP port、MMIO、DMA 和 IRQ 归属都有配置记录 |
| 自动化场景 | 覆盖 normal、drop-ack、retry-exhausted、blackout、out-of-order、invalid-parameter | `scripts/test/net-dual-guest/verify_*.py` | 语义验证和双端 pcap 账本同时闭合 |
| 独立性能数据 | 不启动 AI 模型，单独运行 3×200 完整事务 | `scripts/task2/quantify-benchmark.py` | 600/600，0 重传，0 协议错误，31.834 transaction/s，平均 RTT 31.408 ms |

一个 transaction 必须完整包含 `CONTROL -> ACK -> STATUS -> ACK`。报告中的
吞吐量是完整工业控制事务的完成率，不是 UDP packet/s 或网卡线速。
字节布局、交互时序和指标见 [02-Task2-双Guest通信设计与结果.md](02-Task2-双Guest通信设计与结果.md)。

## 4. Task 3：真实模型到 RTOS 控制的安全闭环

| 要求范围 | 我们完成的工作 | 主要实现位置 | 可观察结果 |
| --- | --- | --- | --- |
| StarryOS 中的神经网络 | 正式物理板运行 RKNN/YOLO 并使用 RK3588 NPU；另有实板 ncnn/CPU 可行性参考和 QEMU ncnn/CPU 可移植替身 | `apps/starry/starryos-task2/rust/src/ncnn/`、`apps/starry/orangepi-5-plus-uvc-rknn/` | 三条路径均有模型加载、张量推理、检测结果和耗时记录；只有 RKNN/NPU 定义正式实板架构 |
| NPU 设备所有权 | NPU MMIO、SPI 110–112、IOMMU、时钟、复位和电源域只归 StarryOS | `scripts/board/task123-zephyr/starry.toml.in`、NPU hybrid 设计文档 | Zephyr 不映射 NPU，计算与控制所有权分离 |
| 模型输出安全门 | 验证置信度、目标面积、坐标、有限值、过期和单步目标变化 | `components/task3-model/src/perception.rs` | 低置信度、小目标、非法输出不会产生 CONTROL |
| 连续场景状态机 | 车辆目标更新跟车输出；行人 hazard 触发 Stop；Stop 锁存；只有显式 Reset 解锁 | `components/task3-model/src/video_safety.rs` | 危险消失后仍保持停车，操作员 Reset 后恢复跟车 |
| 跨 Guest 发送 | 候选决策只能通过 Task 2 的 T2N1 CONTROL 到达 Zephyr | `apps/arceos/task2-net/src/rknn_control.rs`、StarryOS Task 2 endpoint | AI 不能绕过协议直接修改 RTOS 状态 |
| RTOS 可观察动作 | Zephyr 执行 SetOutput、Stop、Reset，保存 Active/Stopped/Safe 状态并回传 STATUS | `scripts/test/net-dual-guest/zephyr-task2/src/main.c` | request ID、action、state、value 可逐事务对账 |
| 端到端时间 | 在 StarryOS 同一 `CLOCK_MONOTONIC` 上记录 inference-start、CONTROL send 和 STATUS receive | `scripts/task3/quantify-hybrid-scene.py` | 分别报告 inference-start→STATUS 和 CONTROL→STATUS，不依赖跨 OS 时钟同步 |
| 固定基线与图像驱动对比 | 固定感知组遍历同一场景序列；RKNN 组在同一架构上使用真实图像 | 场景 manifest、fixed/RKNN init 和量化脚本 | 固定组 24/36 正确，RKNN 组 36/36 正确；hazard recall `0% -> 100%` |
| 真实取舍 | 分开报告准确性、推理时间、通信 RTT 和端到端时间 | 每次运行的 CSV/JSON/原始串口日志 | RKNN 组决策更准确，但图像推理带来额外延迟，不声称所有指标都变快 |

整个场景表达为“厂区物流 AGV 的视觉跟车与行人安全制动”。真实图像、
检测框、控制指令、RTOS 锁存和 Reset 恢复共同构成物理因果链。详见
[03-Task3-推理控制设计与结果.md](03-Task3-推理控制设计与结果.md)。

## 5. StarryOS、QEMU、RTOS 和物理板覆盖

| 系统维度 | 已完成内容 | 说明 |
| --- | --- | --- |
| StarryOS 代替普通 Linux Guest | AI、T2N1 controller、ncnn/RKNN 运行时和 Linux 用户态应用都运行于 StarryOS | 实际使用 StarryOS 的 Linux ABI 兼容能力，不把 StarryOS 写成普通 Linux |
| StarryOS 应用与设备扩展 | 新增 StarryOS Task 2 endpoint、NPU/YOLO 应用、模型运行时与板级配置 | 这些是本系统可直接归属的 StarryOS 工作 |
| StarryOS syscall | 本分支含有广泛的 StarryOS syscall 改进，但本系统只引用实际使用的 ABI 能力 | 不把无法从当前证据确认归属和上游合入状态的 syscall 数量算作本系统新增 |
| QEMU 可复现路径 | 在 AArch64 QEMU 中启动 StarryOS + Zephyr，运行调度、协议故障和 AI 安全场景 | QEMU 数据用于功能、故障注入和相对行为，不冒充 RK3588 NPU 性能 |
| RK3588 物理板路径 | 完成调度 3+3、Task 2 3×200、Task 3 fixed/RKNN 3+3 和 RAM-only 启动 | 实板证明 GIC、定时器、VirtIO、NPU 和双 Guest 组合的实际行为 |
| Zephyr | 作为正式 RTOS Guest 和原生 RTOS 基线，运行 10 ms 周期任务与 T2N1 executor | 正式控制端 |
| RT-Thread 兼容路径 | 保留 RT-Thread endpoint、构建脚本和周期/通信场景 | 用于说明协议和 Guest 边界不锁定单一 RTOS；正式物理板结果仍以 Zephyr 为准 |

## 7. 数据解释边界

- StarryOS 替代 Linux Guest、StarryOS Task 2/AI 应用、QEMU、Zephyr、RT-Thread
  兼容路径和 RK3588 实板都有实际实现。
- QEMU TCG 数据不是物理板硬实时 WCET，CPU ncnn 也不是 RK3588 NPU 性能。
- 原生 Zephyr 数据来自等价 QEMU AArch64 平台；它与 RK3588 实板混合
  系统数据分别解释，不做跨平台绝对值比较。
