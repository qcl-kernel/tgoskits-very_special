# 提交与演示清单

本清单定义从当前 dirty 验证到可提交 clean 证据包的收口条件。未完成的项目不得在总览中提前标为 PASS。

其中“十个行为场景”是本项目自定义的 QEMU `full` 回归矩阵，不是官网规定的场景数量；它用于把官网三项任务拆成可重复、可故障注入的工程验收项。

## 1. 提交前

- [ ] 确认物理拓扑始终写为“一个 2-vCPU StarryOS Linux Guest + 一个 Zephyr RTOS Guest + StarryOS 独占 RK3588 NPU”。
- [ ] 确认 StarryOS vCPU0 是图像/NPU/后处理，vCPU1 是通信/T2N1。
- [ ] 把当前成果材料、配置审计和新证据 manifest 纳入提交，避免它们继续以 untracked 文件改变证据身份。
- [ ] 运行 Markdown 断链、绝对开发机路径和过时场景名检查。
- [ ] 运行格式化、相关 Python/Rust 回归、endpoint clippy、AxVM clippy 和 `git diff --check`。
- [ ] 提交后记录最终 commit ID，不再使用基线 HEAD `b1a9d2375...` 作为最终身份。

## 2. clean QEMU 验收

从 clean worktree 执行：

```bash
scripts/competition/task123.sh doctor
scripts/competition/task123.sh build full
scripts/competition/task123.sh suite full
```

- [ ] `git-status.txt` 为 clean，运行时没有设置 `ALLOW_DIRTY=1`。
- [ ] `ci-contracts` 作为独立 gate 通过，不计入十个行为场景。
- [ ] 十个场景严格是：`task3-yolo-smoke`、`task1-scheduler-ab`、`task2-normal`、`task23-integrated`、`task2-drop-ack`、`task2-retry-exhausted`、`task2-blackout`、`task2-out-of-order`、`task2-invalid-parameter`、`task3-model-rejected`。
- [ ] Task2 六场景均有 `TASK2_MODEL_ISOLATION_PASS`，且无 Task3 模型/推理/检测/实验标志。
- [ ] `task23-integrated` 有真实 YOLO -> CONTROL -> ACK/STATUS 和双 pcap。
- [ ] 最终出现 `TASK123_SUITE_PASS name=full`。
- [ ] 每个场景都保存命令、原始日志、源/运行时配置、pcap、验证器输出、产物/rootfs 哈希和源码身份。

QEMU 运行必须共享 `TASK123_QEMU_LOCK_FILE`。不得在约 15 GiB 主机上并发两个 `-m 8g` QEMU，也不得用放宽 watchdog 代替资源互斥。

## 3. 实板收口

- [x] Task1 periodic RR 3 轮 + FP-RR 3 轮，每轮 300 连续样本，零 deadline miss（dirty 证据）。
- [ ] 使用安全的 Linux/U-Boot fsck 流程处理 ext4 `EUCLEAN`，然后重新证明文件系统健康。
- [ ] 定位并修复 RR 三轮的 `RKNN event sequence does not match the frozen scene`。
- [ ] 从当前 clean commit 重新构建 Guest、AxVisor 和 FIT，不复用历史 FIT 冒充当前产物。
- [ ] 保持 StarryOS vCPU0 -> pCPU2，StarryOS vCPU1 -> pCPU1，Zephyr vCPU0 -> pCPU1，NPU 只归 StarryOS。
- [ ] RAM-only 启动；不执行 flash、erase 或其他持久化写入。

- [ ] 记录 FIT、Guest、DTB、模型、输入、原始串口、pcap 和分析器 SHA-256。
