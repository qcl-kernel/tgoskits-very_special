# 交付物与演示说明

本页只列出当前已经具备的成果，不承载内部工作计划。

## 1. 可运行系统

- 正式物理板拓扑：2-vCPU StarryOS、Zephyr、RK3588 NPU 和 AxVisor。
- QEMU 路径：调度对比、Task 2 正常与故障场景、Task 3 模型闭环与安全拒绝。
- 实板路径：Task 1 正式通信共核对比、Task 2 独立 3×200 事务、Task 3 固定基线组与 RKNN 组对比。
- 原生 RTOS 路径：Zephyr 在等价 QEMU AArch64 平台直接运行，不经过 AxVisor。

## 2. 可展示内容

| 内容 | 展示方式 | 证据来源 |
| --- | --- | --- |
| 完整架构 | pCPU、vCPU、NPU 和设备所有权图 | VM 配置、运行时拓扑与成果材料 |
| Task 1 | RR 组与 FP-RR 组的 P99/P99.9/max 和长尾样本 | 周期日志、CSV、统计报告和图 |
| Task 2 | CONTROL 发出后 ACK、STATUS 和数值在 Zephyr 侧出现 | 双端日志、pcap、事务 CSV/JSON 和实时面板 |
| Task 3 | 真实图片、检测框、固定基线动作、RKNN 动作、Stop 锁存和 Reset 恢复 | 场景图片、NPU 日志、T2N1 事务和状态回传 |
| 故障恢复 | 丢 ACK、重试耗尽、断网、乱序、非法参数和模型输出拒绝 | QEMU 故障注入日志与验证器 |

Task 2 的吞吐量使用完整事务定义：

```text
CONTROL -> ACK -> STATUS -> ACK
```

因此 `31.834 transaction/s` 是每秒完成的工业控制闭环事务数，不是 UDP
包速率。Task 3 的展示页面是原始证据重放；它不会把动画位置解释成真实车辆
运动测量。

## 3. 证据组成

每组正式结果按实际运行能力保存以下材料：

- 原始串口输出和命令记录；
- 运行时 TOML、DTB/FIT/Guest/模型身份；
- QEMU 场景的双端 pcap；
- CSV、JSON、Markdown 汇总和可视化；
- 源码身份、产物哈希和 SHA-256 索引；
- 机器可判定的样本数、协议闭合和成功标志。

物理板启动统一使用 RAM-only `fastboot stage`，不执行 flash 或 erase。
串口监听和 U-Boot 抢占准备完成后，脚本才输出
`BOARD_RESET_REQUIRED` 请求现场按一次 RST。

## 4. 演示顺序

1. 用架构图说明 StarryOS vCPU0、StarryOS vCPU1、Zephyr 与 NPU 的职责。
2. 展示 Task 1 正式实板结果，并用高竞争和无竞争数据解释机制边界。
3. 展示 Task 2 的字段图、完整事务、独立吞吐量和一个故障恢复场景。
4. 播放 Task 3 场景：跟车调整、行人急停、危险消失后锁存、显式 Reset。
5. 打开原始日志、CSV/JSON、pcap 和 SHA-256，说明画面如何回溯到证据。
