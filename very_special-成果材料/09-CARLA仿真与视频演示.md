# CARLA 五场景仿真与视频演示

## 1. 为什么增加独立仿真

Task 1–3 的串口、日志、CSV 和 JSON 能证明调度、通信与推理控制链正确，但仅看
数字不容易直观理解“检测结果最终是否让车辆安全停车”。因此项目增加交通仿真，
把以下完整因果关系放到可观察的道路场景中：

```text
车辆/行人出现 -> YOLO 检测 -> 安全决策 -> Stop/Reset -> 车辆行为 -> 碰撞与净距
```

仿真不是替代真实板卡实验，而是把板卡上已经验证的 NPU 推理、T2N1 通信和
RTOS 控制语义转换成容易观看和比较的交通行为。真实板卡仍负责硬件性能与通信
证据，CARLA 负责道路行为和 A/B 效果展示。

## 2. 为什么选择 CARLA

最终仿真软件为 **CARLA 0.9.16**。选择它主要基于以下工程需求：

- **交通对象完整**：原生支持道路、车辆、行人、天气、交通区域和多种传感器，
  不需要用方块或二维贴图假装真实交通参与者；
- **传感器可验证**：车载 RGB 相机为 YOLO 提供输入，collision sensor 独立记录
  实际碰撞，结果不只依赖程序自己声明“是否安全”；
- **场景可控**：Python API 可以固定本车、障碍车、行人、天气和事件顺序，保证
  固定基线与 YOLO 闭环在相同故事下进行 A/B 对比；
- **适合闭环控制**：脚本可以逐帧读取相机、运行检测、调整车辆控制并记录状态，
  能表现 `RUN -> STOP -> CONFIRM -> RESET -> RESUME -> RUN`；
- **结果可追溯**：每次运行同时输出视频、逐帧 JSON、事件序列、碰撞次数、目标
  距离和推理时间，便于从演示画面回到原始数据。

早期的二维合成画面和简单物理方块只适合验证流程，无法自然表达行人横穿、车辆
切入、遮挡关系和复杂路口，因此没有作为最终展示方案。

## 3. A/B 对比方法

每个场景分别运行两个独立分支，二者使用相同道路、天气与障碍物故事：

- **A：固定基线**——车辆保持固定控制输出，不根据前方车辆或行人避让；
- **B：YOLO 闭环**——主机 ONNX Runtime 执行 YOLO 检测，根据车辆和行人位置
  进行减速或停车，保持 2 秒确认后执行 Reset，并继续行驶约 6 秒证明正常恢复。

车辆与行人使用不同安全尺度：车辆按约 `8 m` 视觉停车间隔控制；行人在约
`30 m` 开始减速、`24 m` 硬停车，并以 CARLA 中车身外沿到行人外沿的实际几何
净距不低于 `2 m` 作为验收线。这样既避免贴近车辆过早停车，也避免对行人停车
过晚甚至发生接触。

## 4. 五个场景

场景从单一静态目标逐步增加到动态目标、遮挡和多人多车混合交通：

| 场景 | 交通故事 | 主要验证点 | 固定基线 | YOLO 闭环 |
| --- | --- | --- | --- | --- |
| 1. 晴天直路静止汽车 | 本车接近同车道静止汽车 | 基础车辆检测与停车 | 碰撞 | 安全停车、Reset、恢复，零碰撞 |
| 2. 斑马线行人横穿 | 行人进入本车行驶区域 | 行人提前减速与安全净距 | 碰撞 | 最小净距 `2.223 m`，零碰撞 |
| 3. 前车切入并制动 | 动态车辆切入后成为前向障碍 | 动态目标跟踪与响应 | 碰撞 | 跟踪停车、危险解除后恢复，零碰撞 |
| 4. 货车遮挡行人 | 行人在货车遮挡条件下进入危险区域 | 遮挡场景中的安全响应 | 碰撞 | 最小净距 `14.104 m`，零碰撞 |
| 5. 多车多人复杂路口 | 多辆车、多人和背景目标同时出现 | 相关危险目标选择与完整闭环 | 碰撞 | 最小净距 `2.217 m`，零碰撞 |

最终汇总结果为：固定基线 `5/5` 发生碰撞；YOLO 闭环 `5/5` 碰撞数为 0。
五个 YOLO 场景均完整经过停车、确认、Reset、恢复，并在 Reset 后继续行驶约
`6.03 s`，而不是刚起步就结束视频。

## 5. 视频内容与数据叠加

视频不是只显示车辆画面。YOLO 分支同步展示以下关键数据：

- 主机 YOLO/ONNX 单帧推理时间和检测目标；
- RK3588 NPU 代表帧运行时间与完整推理流水线时间；
- T2N1 CONTROL、ACK、STATUS、request ID 和通信耗时；
- 当前控制状态：RUN、STOP、CONFIRM、RESET、RESUME；
- Stop 保持时间、Reset 回到 Active 的时间；
- 碰撞次数、车辆/行人距离和 Reset 后继续行驶时间。

其中 CARLA 交通闭环由主机 ONNX Runtime 驱动；视频中按场景显示的 RK3588
NPU、T2N1 CONTROL/STATUS 和 Reset 回执来自五场景代表帧的真实物理板运行。
两者组成“仿真交通行为 + 实板推理/通信测量”的证据链，但不宣称 CARLA 相机
流逐帧实时传输到了开发板。

本次真实板卡代表帧运行共包含 15 张图片和 20 次状态返回，NPU 平均运行时间为
`18.13 ms`，完整推理流水线平均为 `62.60 ms`，最终验证结果为 PASS。正式板卡
拓扑保持 StarryOS `[0x200, 0x100]`、Zephyr `[0x100]`，NPU 仅归 StarryOS。
