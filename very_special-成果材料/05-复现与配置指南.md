# 复现与配置指南

本文是运行系统的唯一总入口，集中说明命令、参数、成功标志和排障顺序。
系统架构只在 [00-总体架构与设计.md](00-总体架构与设计.md) 定义；各项结果和
原始材料位置见 [06-证据与演示索引.md](06-证据与演示索引.md)。所有命令均从
仓库根目录执行。

## 1. 最短运行路径

### 最简单的 QEMU 启动方式

首次在仓库根目录统一检查环境并构建：

```bash
scripts/competition/task123.sh prepare
scripts/competition/task123.sh doctor
scripts/competition/task123.sh build full
```

然后按任务分别启动。每个命令只产生本任务的汇总、PASS 和证据目录：

```bash
# Task 1：4 组——空载 RR/FP-RR、压力 RR/FP-RR
scripts/competition/task123.sh suite task1

# Task 2：6 个 Task2-only 正常/故障通信场景
scripts/competition/task123.sh suite task2

# Task 3：2 个模型场景
scripts/competition/task123.sh suite task3
```

三项分别输出 `TASK123_SUITE_PASS name=task1`、`name=task2`、`name=task3`，并
分别写入独立的 `suite-task1`、`suite-task2`、`suite-task3` 证据目录。Task 2+3
联合闭环属于跨任务核验，单独执行：

```bash
scripts/competition/task123.sh run task23-integrated
```

`suite acceptance` 和 `suite full` 仅作为可选的自动化回归入口，不作为人工查看
Task 1–3 结果的推荐方式。

全新 checkout 运行 QEMU 时必须先执行 `build full`。只有当同一 checkout
已完成该构建且产物未改变时，才能直接重跑 suite。提交的 FIT 只服务实板
RAM 启动，不替代 QEMU 的 StarryOS、Zephyr、rootfs 和模型构建。

`prepare` 还会根据固定 Zephyr revision 的 `scripts/requirements-base.txt` 在
`.deps/task123/` 创建专用 Python 虚拟环境。Task 1/2 的 Zephyr CMake 均显式绑定
该解释器，避免依赖宿主机碰巧安装的包。`doctor` 会在构建前检查其中的
`jsonschema`、`PyYAML`、`pykwalify`、`pyelftools` 和 `packaging`；若显示
`MISSING`，先按
[`scripts/competition/README-task123.md`](../scripts/competition/README-task123.md)
准备对应的固定 revision 源码、模型或工具链。`build full` 保留下载内容，但从当前
源码重新生成产物；`suite` 中任一场景失败都会非零退出。可用
`scripts/competition/task123.sh --list` 查看全部入口；各任务的场景含义和故障注入
范围见 [04-QEMU分任务验证.md](04-QEMU分任务验证.md)。

如需使用已有 Python 环境，可显式设置 `TASK123_PYTHON=/path/to/python3`。该覆盖
是强制的：依赖不完整时命令会明确列出缺包且非零退出，不会回退到另一解释器。
不建议直接向系统 Python 全局安装 `jsonschema`，因为这不能保证老师机器和复现
机器实际选择同一个解释器。

VS Code 的 `Terminal -> Run Task` 提供对应的 Task 1、Task 2、Task 3 和完整验证
入口，它们调用同一个 `scripts/competition/task123.sh`，不存在第二套运行逻辑。

## 2. 物理板运行

### 最简单的实板启动方式

连接 ATK-DLRK3588 的串口、USB/fastboot 和电源后，在仓库根目录按要核验的任务
分别执行：

```bash
# Task 1
scripts/competition/task123.sh board task1-communication

# Task 2
scripts/competition/task123.sh board task2-throughput

# Task 3
scripts/competition/task123.sh board task3-matrix
```

上述入口默认使用 [`board-fits/`](board-fits/README.md) 中已提交的五个
RAM 启动产物。首次启动前可执行：

```bash
cd very_special-成果材料/board-fits
sha256sum -c SHA256SUMS.txt
cd ../..
```

原生 RTOS 是 Task 1 的平台基线，单独运行，不与上述三个正式实板入口混合：

```bash
scripts/competition/task123.sh board native
```

从源码完整构建 Task 3 需要显式提供外部产物：

```bash
TASK123_BUSYBOX_STATIC=/path/to/aarch64-busybox \
TASK123_RKNN_BUNDLE=/path/to/rknn-bundle \
TASK123_BOARD_DTB=/path/to/atk-dlrk3588-starry.dtb \
  scripts/competition/task123.sh board task3-all
```

实板入口只允许 RAM-only `fastboot stage`，不执行 flash 或 erase。脚本先独占
串口、启动日志抓取并持续发送 Ctrl-C；只有看到下面的提示时，操作者才按一次
物理 RST：

```text
BOARD_RESET_REQUIRED: press the physical RST button once now.
```

脚本捕获 U-Boot 后会自动完成 RAM 启动，不需要人工抢 Reset 与 Ctrl-C 的时序。
默认串口为 `/dev/ttyACM0`，波特率为 1500000；多板环境必须设置
`TASK123_BOARD_FASTBOOT_SN`。因此实板是“一条命令 + 必要时按一次 RST”的协作式
启动，不应描述成完全无人值守；脚本会继续完成 RAM 装载、运行、日志保存和结果核验。

## 3. 成功标志

| 阶段 | 必须观察到的事实 |
| --- | --- |
| Guest 启动 | StarryOS 和 Zephyr 均进入运行态，无 panic、ESR 或 Guest fatal |
| Task 1 | 样本数精确；采样结束后压力和通信仍推进；A/B 两组除调度策略外拓扑一致 |
| Task 2 | `transactions=200 pending=0 errors=0`，CONTROL/ACK/STATUS/ACK 对账闭合 |
| Task 3 固定基线 | 固定输出遍历完整事件序列，并获得 RTOS 状态回传 |
| Task 3 RKNN | NPU 推理、CONTROL、ACK/STATUS、Stop 锁存和显式 Reset 全部出现 |
| QEMU Task 1 | 独立输出 `TASK123_SUITE_PASS name=task1`，4 组调度运行均通过 |
| QEMU Task 2 | 独立输出 `TASK123_SUITE_PASS name=task2`，6 个通信场景均通过 |
| QEMU Task 3 | 独立输出 `TASK123_SUITE_PASS name=task3`，2 个模型场景均通过 |

验证器不仅检查退出码，还检查样本数、协议序列闭合、模型隔离、安全状态、产物
身份和 fatal marker。不能通过放宽 watchdog、减少期望样本或删除失败记录绕过
前一层错误。

## 4. 配置与硬编码边界

仓库根目录由脚本位置推导，不依赖调用者当前目录，也不把开发者用户名写入可执行
配置。常用覆盖字段如下：

| 类别 | 环境字段 |
| --- | --- |
| 交叉工具链 | `CROSS_ROOT`、`CROSS_CC`、`CROSS_CXX`、`CROSS_AR`、`CROSS_RANLIB`、`CROSS_COMPILE` |
| 外部源和模型 | `NCNN_SOURCE`、`ZEPHYR_BASE`、`PNNX`、`YOLO_ONNX`、`TASK3_NCNN_INPUT` |
| 证据与临时目录 | `TASK123_EVIDENCE_DIR`、`TASK123_RUNTIME_PARENT`、`TASK123_ROOTFS_RUNTIME_PARENT` |
| QEMU 互斥 | `TASK123_QEMU_LOCK_FILE`、`TASK123_QEMU_LOCK_TIMEOUT_SEC` |
| Guest 输入 | `STARRY_TASK23_ROOTFS`、`STARRY_TASK23_HOST_CONFIG`、`STARRY_TASK23_QEMU_CONFIG`、`STARRY_TASK23_STARRY_VM_CONFIG`、`STARRY_TASK23_RTOS_VM_CONFIG`、`TASK3_YOLO_ASSETS` |
| RTOS 选择 | `STARRY_TASK23_RTOS_NAME`、`STARRY_TASK23_RTOS_IMAGE`、`STARRY_TASK23_RTOS_SOURCE_DIR` |
| 实板选择 | `TASK123_BOARD_PORT`、`TASK123_BOARD_BAUD`、`TASK123_BOARD_FASTBOOT_SN`、`TASK123_BOARD_BREAK_WINDOW` |
| 实板产物 | `STARRY_KERNEL`、`STARRY_INITRD`、`ATK_HOST_DTB`、`TASK123_BOARD_DTB`、`TASK123_RKNN_BUNDLE` |

`prepare` 生成的工具链和 Zephyr 默认位于 `.deps/task123/`，统一入口会自动发现。
ncnn、pnnx 与模型可放在仓库的临时目录并显式指定：

```bash
export NCNN_SOURCE="$PWD/tmp/competition-task123/downloads/ncnn"
export PNNX="$PWD/tmp/competition-task123/downloads/pnnx-20260526-linux/pnnx"
export YOLO_ONNX="$PWD/tmp/competition-task123/downloads/yolo11n.onnx"
```

若需要显式指定 `prepare` 生成的依赖，则使用：

```bash
export CROSS_ROOT="$PWD/.deps/task123/aarch64-linux-musl-cross"
export ZEPHYR_BASE="$PWD/.deps/task123/zephyr-dccb09599635bdff17633fa7e9dab014b91dce90"
```

`10.0.42.15/24`、`10.0.42.2/24`、UDP `4242` 和 Guest 模型目录
`/usr/share/task3-yolo` 属于双 Guest 线协议或镜像 ABI。它们不是开发机路径，
不能由单端环境变量静默修改；若改变，必须同步更新两端、fixture、pcap verifier
和镜像构建。

完整字段和兼容入口见
[`scripts/competition/TASK123-CONFIG-AUDIT.md`](../scripts/competition/TASK123-CONFIG-AUDIT.md)，
外部依赖说明见
[`scripts/competition/README-task123.md`](../scripts/competition/README-task123.md)。

## 5. 运行隔离与资源边界

QEMU/AxVisor 的运行时 TOML 会包含本次实际 rootfs、Guest 和 socket 的绝对路径；
它们由输入动态渲染，不是仓库硬编码。每次运行使用独立临时目录、可写 rootfs
副本、serial/QMP socket 和 pcap，清理时只处理本次 PID，不使用全局
`pkill` 或 `killall`。

单个验收 QEMU 使用 `-m 8g`。统一入口用 `TASK123_QEMU_LOCK_FILE` 的 `flock`
串行化高内存场景，避免多个实例耗尽主机内存和 swap 后触发串口 watchdog 假
超时。等待上限由 `TASK123_QEMU_LOCK_TIMEOUT_SEC` 控制。

正式 Task 1 入口使用“通信 vCPU 与 RTOS 共核”的冻结拓扑。AI 与 RTOS 共核只
保留为明确标注的高竞争消融入口，不进入正式结果或演示。

## 6. 排障顺序

```text
入口与依赖
  -> 串口独占、端口和波特率
  -> Reset 后是否抢到 U-Boot
  -> fastboot 设备与 RAM-only FIT stage
  -> FIT、DTB、Guest 哈希与 CPU 映射
  -> StarryOS 和 Zephyr 是否启动
  -> StarryOS NPU/RKNN 初始化
  -> VirtIO-net、IP、UDP 4242 与 T2N1
  -> CONTROL/ACK/STATUS 状态机
  -> 量化器、CSV/JSON 与展示产物
```

原生 Zephyr/QEMU 只表示不经过虚拟层的等价平台基线；QEMU TCG 的绝对时间不
代表 RK3588 NPU 或实板硬实时性能。
