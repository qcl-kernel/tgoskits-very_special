# 总体架构与设计

## 物理板混合拓扑

当前 ATK-DLRK3588 拓扑是一个 2-vCPU StarryOS Linux Guest、一个 Zephyr RTOS Guest 和一个独占归 StarryOS 的 RK3588 NPU。所谓“图像 Linux”和“通信 Linux”是同一 StarryOS Guest 中的两个 vCPU 职责域，绝不是两个 Linux Guest。

```text
AxVisor RR / bounded FP-RR
├── StarryOS Linux Guest (2 vCPU, priority 89 under FP-RR)
│   ├── vCPU0 -> pCPU2: 启动、图像预处理、RKNN/NPU 提交、后处理
│   ├── vCPU1 -> pCPU1: virtio-net、T2N1、CONTROL/STATUS、通信 IRQ
│   └── RK3588 NPU: YOLO 张量推理，只归 StarryOS
└── Zephyr RTOS Guest (1 vCPU, priority 90 under FP-RR)
    └── vCPU0 -> pCPU1: 10 ms 周期任务、控制执行、ACK/STATUS
```

StarryOS vCPU1 与 Zephyr vCPU0 共享 pCPU1。FP-RR 下 Zephyr 以优先级 90 抢占 StarryOS 通信 vCPU 的优先级 89；StarryOS vCPU0 在 pCPU2 处理 AI 主路，避免图像预处理和后处理直接堵住 RTOS。

NPU 不取代 CPU：解码、resize/letterbox、颜色转换、RKNN runtime 调用和 NMS 仍由 StarryOS CPU 执行。NPU MMIO、IRQ、IOMMU、时钟、复位和电源域依赖不得同时分配给 Zephyr 或 host。

## 三个任务的系统主线

```text
图像 -> StarryOS vCPU0 + RK3588 NPU -> 检测/安全校验/限幅
                                              |
                                              v
StarryOS vCPU1 -- T2N1 CONTROL --> Zephyr -- ACK/STATUS --> StarryOS vCPU1
                         ^              |
                         |              +-- 10 ms 周期任务
                   AxVisor FP-RR 保障共享 pCPU1
```

- Task 1 解决 AI/通信负载与 RTOS 共享 CPU 时的实时唤醒、中断退出和低优先级有界服务。
- Task 2 在独立 MMIO、DMA、stage-2 和 vIRQ 边界上提供双 Guest 可靠 CONTROL/STATUS 通道。
- Task 3 把真实模型输出经语义校验和单步限幅后转成控制量，并对错误输出 fail-safe。

## QEMU 可移植替身拓扑

QEMU 保留“一个 StarryOS Guest + 一个 Zephyr Guest + AxVisor 内部 virtio-net switch”的功能边界，但使用 Guest 内 AArch64 CPU ncnn/YOLO 代替 RK3588 RKNN/NPU。因此 QEMU 用于可复现功能、协议故障、控制安全和相对调度行为，不是 NPU 性能证据。

Task 2 六场景还显式使用 `STARRY_TASK23_SCOPE=task2`，不安装、加载或运行 YOLO；`task23-integrated` 才是同时验证 Task 2 与 Task 3 的推理控制联合闭环。

## 声明边界

- QEMU TCG 数据不是物理板硬实时 WCET 保证。
- NPU/YOLO 改善感知与安全决策能力；FP-RR 改善 RTOS 唤醒确定性，不宣称缩短张量计算本身。
- 当前分支实板 Task 1 periodic 已复测，但 Task 2/3 实板完整矩阵尚未完成。
- 迁移前 RKNN/NPU 数据仅作历史可行性与已观察边界，不得冒充当前 clean commit 的新证据。
