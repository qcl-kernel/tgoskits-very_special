# 总体架构与设计

## 物理板正式架构（唯一主线）

当前 ATK-DLRK3588 正式拓扑只有一个 2-vCPU 的类 Linux StarryOS
Guest、一个 Zephyr RTOS Guest，以及只归 StarryOS 所有的 RK3588
NPU。“AI CPU”与“通信 CPU”是同一 StarryOS Guest 内的两个 vCPU
职责域，不是两个 Linux Guest。NPU 是加速器，不是第三颗 pCPU。

```text
                              RK3588
+--------------------------------------------------------------------+
|                                                                    |
|  pCPU2：AI 计算域                                                   |
|  +--------------------------------------------------------------+  |
|  | 类 Linux StarryOS vCPU0（Guest CPU 0）                      |  |
|  | 图像预处理 -> RKNN 提交 -> NPU -> 后处理/安全决策     |  |
|  +--------------------------------------------------------------+  |
|                            |                                       |
|                            | 候选控制决策                          |
|                            v                                       |
|  pCPU1：实时通信竞争域                                             |
|  +------------------------------+  +----------------------------+  |
|  | 类 Linux StarryOS vCPU1     |  | Zephyr RTOS vCPU0          |  |
|  | VirtIO-net / T2N1            |  | 10 ms 周期任务             |  |
|  | CONTROL / STATUS / ACK       |  | 控制执行、ACK/STATUS        |  |
|  | priority 89                  |  | priority 90                |  |
|  +------------------------------+  +----------------------------+  |
|                  \                    /                           |
|                   +---- 共享 pCPU1 ----+                           |
|                        AxVisor bounded FP-RR                      |
|                                                                    |
|  RK3588 NPU：只归 StarryOS；Zephyr 和 AxVisor host 均不映射       |
+--------------------------------------------------------------------+
```

StarryOS vCPU1 与 Zephyr vCPU0 共享 pCPU1。FP-RR 下 Zephyr 以优先级
90 抢占优先级 89 的 StarryOS 通信 vCPU；有界服务窗口又保证通信
Guest 不被饿死。StarryOS vCPU0 在 pCPU2 处理 AI 的 CPU 侧工作，
避免解码、预处理和 NMS 的长 burst 直接堵住 RTOS。

NPU 不取代 CPU：解码、resize/letterbox、颜色转换、RKNN runtime
调用和 NMS 仍由 StarryOS vCPU0 执行。NPU MMIO、IRQ、IOMMU、时钟、
复位和电源域依赖不得同时分配给 Zephyr 或 host。

## 三个任务的系统主线

```text
真实图像
   |
   v
StarryOS vCPU0 / pCPU2
   +-> 图像预处理 -> RKNN runtime -> RK3588 NPU -> 检测/安全校验/限幅
                                                        |
                                                        v
StarryOS vCPU1 / pCPU1 -- T2N1 CONTROL --> Zephyr / pCPU1
          ^                                      |
          |                                      +-> 10 ms 周期任务和控制执行
          +--------------- ACK/STATUS -----------+
                              ^
                              |
                     AxVisor bounded FP-RR
```

- Task 1 解决正式通信共核下 RTOS 的实时唤醒、中断退出和低优先级有界服务。
- Task 2 在独立 MMIO、DMA、stage-2 和 vIRQ 边界上提供双 Guest 可靠 CONTROL/STATUS 通道。
- Task 3 把真实模型输出经语义校验和单步限幅后转成控制量，并对错误输出 fail-safe。

## 为什么这样设计

系统同时面对三个不同目标：AI 需要计算吞吐，RTOS 需要尾延迟确定性，
控制通信又必须持续前进。把 AI 与 RTOS 放在同一 pCPU 会制造强竞争，
能放大调度优化的相对收益，但会让产品本身的实时基线变差。因此正式设计是：

1. 用 pCPU2 + NPU 承担 AI 主路，先做空间隔离；
2. 只让与控制闭环直接相关的通信 vCPU 与 Zephyr 共享 pCPU1；
3. 用 bounded FP-RR 做时间隔离：RTOS deadline 优先，通信又不饿死。

这不是为了追求最大的“优化倍数”，而是追求优化后的整体架构可用性。

## 主线、高竞争参考与无竞争基线

```text
正式主线：     AI/NPU @ pCPU2，通信 + Zephyr @ pCPU1
                 RR P99 0.621 ms -> FP-RR P99 0.278 ms（降低 55.3%）

高竞争参考： AI CPU 工作 + Zephyr 共核
                 QEMU P99 14.291 ms -> 1.091 ms（约 13.1x）

无竞争基线： Zephyr 没有持续共核竞争者
                 RR 与 FP-RR 接近，用于界定优化的适用条件
```

| 层级 | 共核工作 | 证明什么 | 证据定位 |
| --- | --- | --- | --- |
| 正式主线 | StarryOS 通信 vCPU + Zephyr | 真实部署架构下的调度收益 | 正式统计与报告主结论 |
| 高竞争参考/ablation | AI 的 CPU 侧预处理/后处理 + Zephyr | 强干扰下 FP-RR 的机制上限 | 参考结果，不代表产品拓扑 |
| 无竞争基线 | Zephyr 无持续竞争者 | 没有竞争时两种调度策略接近 | 基线，不冒充优化证据 |

高竞争实验的相对提升更大，是因为它的 RR 基线被 AI CPU burst
干扰得更严重，不能由此推导出它是更好的系统架构。两组数据还来自
不同平台，只在各自同拓扑 RR/FP-RR A/B 内比较，不做跨平台绝对值比较。

## QEMU 可移植替身拓扑

QEMU 保留“一个 StarryOS Guest + 一个 Zephyr Guest + AxVisor 内部 virtio-net switch”的功能边界，但使用 Guest 内 AArch64 CPU ncnn/YOLO 代替 RK3588 RKNN/NPU。因此 QEMU 用于可复现功能、协议故障、控制安全和相对调度行为，不是 NPU 性能证据。

Task 2 六场景还显式使用 `STARRY_TASK23_SCOPE=task2`，不安装、加载或运行 YOLO；`task23-integrated` 才是同时验证 Task 2 与 Task 3 的推理控制联合闭环。

## 声明边界

- QEMU TCG 数据不是物理板硬实时 WCET 保证。
- NPU/YOLO 改善感知与安全决策能力；FP-RR 改善 RTOS 唤醒确定性，不宣称缩短张量计算本身。
- Task 1 正式通信共核已完成 RR/FP-RR 各 3 轮，每轮
  6000×10 ms；Task 2 已完成实板 3×200 有界吞吐；Task 3 已完成
  固定基线/RKNN 各 3 轮。
- `ai-share` 只是高竞争参考/ablation，不进入正式实板统计、Demo 或主结论。
- 原生 RTOS 基线是在等价 QEMU AArch64 平台直接运行 Zephyr，和
  RK3588 实板混合系统数据分开报告。
